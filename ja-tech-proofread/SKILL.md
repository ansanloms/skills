# 日本語技術文章の推敲

日本語の技術文書 (markdown) を読み、機械判定できない層の問題を直す。対象は段落と論証の構成、箇条書き項目の書き方、文の一義性、語彙、事実と意見の区別で、局所的な修正はファイルへ適用し、構成の変更は箇所・規範 ID・理由・修正案の一覧として返す。文書を書き上げた著者、または著者に代わって文書を確認するエージェントが、公開・コミット前の確認に使う。

## 分担

- 表記と文法の機械判定は textlint (`textlint-rule-preset-ansanloms`) が担う。lint 設定は `scripts/.textlintrc.js` (preset をそのまま有効化) で、この skill が rule を上書きすることは無い。textlint が出した指摘は機械層として報告に転記し、この skill は再判定しない。
- preset が無効化した rule のうち、この skill が意味の側から引き取るのは `ja-no-weak-phrase` (S2) と `no-doubled-joshi` (S3) の 2 つ。この 2 つは機械判定では誤検出が出るため preset が無効化している。S 群の他の規範は、有効な rule と重ならない範囲を扱う。
- それ以外に lint が拾わない表記・文法の現象 (括弧の幅、カタカナ長音、外来語の表記等) があっても、この skill は表記・文法を判定しない。rule の有効・無効の一覧は preset の README を正とする。
- 文体 (常体か敬体か) は扱わない。文体は lint 設定が決める。

## 受け取り

Skill ツールの `args` を次の文法で解釈する。

```
<mode> <path...>
```

- `mode`: `fix` または `lint`。省略時は `fix`。
  - `fix`: 機械層を `--fix` で直し、局所修正 (規範 S・H・R・L3〜L5) をファイルへ直接適用する。構成変更 (規範 D・P・L1・L2・L6・L7) は指摘と修正案に留める。
  - `lint`: ファイルを変更せず、すべての指摘を一覧で返す。
- `path...`: 対象ファイルの絶対パス。複数渡された場合は、機械層の実行・推敲・報告をファイルごとに分けて行い、会話にはファイルごとに 1 行ずつ返す。省略時は会話で指定された対象 (ファイルパスまたは貼り付けられた本文) を使う。見出し名や行範囲の指定があればその範囲だけを見る。範囲指定があっても機械層 (textlint と deno fmt) はファイル全体に効き、範囲外の自動修正も集計の M に含める。貼り付け本文が対象の場合は、報告ファイルと同じ出力ディレクトリ (「報告書式」節。1 回の実行で 1 回だけ確保する) に `input-<YYYYMMDD-HHMMSS>.md` として書き出し、以後はそのファイルを対象として扱う。報告ヘッダの対象には「貼り付け本文 (一時ファイル <絶対パス>)」と書く。`fix` モードでは修正後の一時ファイルの内容を報告の「修正後の全文」に置く。報告ファイルは同じタイムスタンプで `proofread-input-<YYYYMMDD-HHMMSS>.md` とする。

description による自動発動で `args` が無い場合は、mode を `fix`、path を会話文脈から取る。

### スクリプトの場所

機械層は `scripts/` の textlint で実行する。実行のたびに次のループを 1 回だけ走らせて絶対パスを解決し、以後は結果をリテラルで書き下す。理由: エージェントのシェルは呼び出しごとに cwd と変数を失う。

```sh
for d in "$PWD/.claude/skills/ja-tech-proofread" "$HOME/.claude/skills/ja-tech-proofread" "$PWD/ja-tech-proofread"; do
  if [ -d "$d/scripts" ]; then echo "$d/scripts"; break; fi
done
```

候補の順は、配布先 (`apm install` 後)、ユーザ共通、このリポジトリ内。最初に見つかった 1 件を使う。0 件なら推測せず、機械層を「実行不可 (scripts 未検出)」として手順 1 へ進む。内部動作は `scripts/README.md` を参照。

## 手順

0. 機械層。対象が複数なら path ごとに行う。`<scripts>/deno.json` の `imports` から preset の alias 先 URL を控え、報告ヘッダに使う。`lint` モードは (a) `deno task -q --cwd "<scripts>" textlint <path>` を実行して出力 O と終了コードを得て、(b) `deno task -q --cwd "<scripts>" fmt:check <path>` を実行して整形差分の有無を得る。自動修正の件数 M は 0。`fix` モードは (a) `--fix` 付きの textlint を実行して出力 O1 から M を取り (`✔ Fixed N problem` の行があれば N、無ければ 0。実物の例: `✔ Fixed 1 problem`。取得コマンド `deno task -q --cwd "<scripts>" textlint --fix <probe>`、取得日 2026-08-31)、(b) `deno task -q --cwd "<scripts>" fmt <path>` を実行して整形し、(c) `deno task -q --cwd "<scripts>" textlint <path>` (`--fix` 無し) を実行して出力 O2 を得る。O1 は実行可否の判定にだけ使い、`No rules found` を含めば実行不可として (b) (c) は行わない。指摘件数の分類は O (`lint`) または O2 (`fix`) にだけ当てる。解釈・要約・再判定はしない。
   - 実行不可: 出力に `No rules found` を含む、または終了コードが 2 以上 (対象が見つからない場合の `Not found target files` 等)。報告には「実行不可 (理由)」と書き、以降の手順は続行する。
   - 指摘あり: 上記以外で終了コードが 1。残り件数 K は `✖ N problem` または `✖ N problems` の行の N (1 件のときは単数形で出る)。
   - 0 件: 終了コードが 0。warning や info の行だけが出ていても 0 件とする。K は 0。報告には出力をそのまま貼った上で「指摘 0 件 (終了コード 0)」と書く。
   - 整形: `fmt`/`fmt:check` は skill 自身の設定 (`scripts/deno.json`、`proseWrap: preserve`) で動き、対象が属するプロジェクトの fmt 設定と除外は見ない。`fmt` が 0 以外、`fmt:check` が 0 と 1 以外の終了コードで終わった場合 (対象が見つからない等) は、整形は実行不可とし「整形: 実行不可 (理由)」と書き、textlint の結果はそのまま扱う。

   集計の機械層は「自動修正 M 件、整形あり | 整形なし、残り K 件」と書く。整形は `fix` モードでは `deno fmt` がファイルを変更したか、`lint` モードでは `fmt:check` が差分を報告したかで決める。実行不可のときは「機械層 (実行不可)」と書く。
1. 節の分割と種別判定。見出し (`#` で始まる行。コードフェンス内の行は除く) ごとに節を切る。見出しが無い文書は全体を 1 節とする。各節について、見出し行・表・コードフェンス・frontmatter を除いた非空行のうち、箇条書き行 (`-`、`*`、`1.` 等で始まる行と、そのインデント継続行) が過半なら「項目」、そうでなければ「散文」とする。判定対象の非空行が 0 の節は「散文」とする。
2. pass 1 (構成)。規範の適用 (手順 2〜4) では、表・コードフェンス・frontmatter の中身を対象から除く。D 規範を文書全体に当てる。P 規範は散文の節に当て、項目の節に並置された独立の散文段落にも当てる。L 規範を項目の節に当て、R 規範を全節に当てる。
3. pass 2 (文と語彙)。S 規範と H 規範を全節に当てる。
4. 適用。`fix` モードなら、pass 1・pass 2 で見つけた局所修正 (S・H・R・L3〜L5) をファイルへ適用する。構成変更は適用しない。`lint` モードなら何も適用しない。
5. 報告。「報告書式」に従って組み立てる。箇所の行番号は手順 0 完了後・手順 4 適用前のファイルを基準にする。

pass 1 を pass 2 より先に回す。理由: 構成の修正 (段落の分割・項目の統合) で文そのものが消えるため、文の修正を先に出すと無駄になる。

## 規範

各規範は ID で参照する。「適用」列は当てる節種別、「出典」列は規範の根拠を示す。出典の詳細は [references/sources.md](references/sources.md) にある。`fix` モードで直接適用する群は S・H・R と L3〜L5、指摘に留める群は D・P と L1・L2・L6・L7。

### D: 文書 (指摘に留める)

| ID | 規範                                                                                                                                                                 | 適用 | 出典            |
| -- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---- | --------------- |
| D1 | 冒頭の 1 段落で、何を扱い、いつ使うかを言う。読み手は、文書の型や置き場所 (README、PR 本文等) から決まらない場合にだけ書く                                           | 文書 | Google style    |
| D2 | 結論と判断を先に置き、根拠と経緯を後に置く。根拠や経緯に相当する記述が無い短い文書には当てない                                                                       | 文書 | 木下 (重点先行) |
| D3 | 見出しは扱う対象を指す名詞句にする。1 節が 1 規範だけの仕様文では、規範文そのものを見出しにしてよい                                                                  | 文書 | gist 見出し節   |
| D4 | 同じ主張を 2 か所に書かない。他の文書や節が持つ内容は参照で済ませ、転記しない                                                                                        | 文書 | gist 冗長節     |
| D5 | 節の順序は 目的 → 前提 → 本体 (手順・規範・論証) → 例外 → 根拠 とする。根拠を本体の前に長く置かない                                                                  | 文書 | 文化庁、Google  |
| D6 | 読み手が参照しない固有名・数値・詳細を出さない。「参照しない」とは、文書内で再登場せず、手順の実行にも要らないことを指す。例を足すときは、前の例との差分を前置きする | 文書 | gist 負荷節     |

| -- | ---------------------------------------------------------------------------------------------------------------------------------- | ---- | ----------- |

| P2 | 段落の先頭で前段との関係を接続表現で示す。関係が文脈から読めるなら省いてよい。1 文だけの段落には当てない                           | 散文 | gist        |

| P4 | 因果を書くときは機構を一文添える。単一の原因に還元しない                                                                           | 散文 | gist        |

### L: 項目

大半は執筆コーパス (ルール文書・skill 本文) の実態から起こしたもので、公開基準に対応があるものは根拠列に併記する。L1・L2・L6・L7 は指摘に留め、L3〜L5 は `fix` モードで適用する。

| ID | 規範                                                                                                                                                 | 適用 | 根拠                                                |
| -- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ---- | --------------------------------------------------- |
| L1 | 1 項目 1 規範。強度 (MUST・推奨・禁止・任意) を語で明示する。強度の無い項目は事実の記述として読める形にする                                          | 項目 | 走査して読む前提                                    |
| L2 | 条件 → 帰結の順に書く。例外は同じ項目内に置き、別の項目や節に散らさない。条件を持たない項目には当てない                                              | 項目 | Google (条件を指示の前に)、散らすと参照時に見落とす |
| L3 | 括弧による補足は 1 文につき 1 つまで。2 つ以上必要なら文を分けるか、下位の箇条書きへ下ろす                                                           | 項目 | 長文の主因が括弧の畳み込み                          |
| L4 | 理由は規範の直後に「理由:」で分離する。規範と理由を 1 文に畳まない                                                                                   | 項目 | 規範だけ読みたい読者が理由を飛ばせる                |
| L5 | 3 つ以上の並列は箇条書きにする。文中の並列は「・」で結び、`/` は選択肢 (どれか 1 つ) に限る                                                          | 項目 | 文化庁 (三つ以上は箇条書き)                         |
| L6 | 1 つの項目の内部に複数の段落を書かない。項目が 4 文以上なら小見出しに昇格して散文の節にする。項目の節に並置された独立の散文段落は対象外 (P を当てる) | 項目 | 散文が混ざると P と L のどちらを当てるか決まらない  |

| ID | 規範                                                                                                                                                    | 適用 | 根拠                                                  |
| -- | ------------------------------------------------------------------------------------------------------------------------------------------------------- | ---- | ----------------------------------------------------- |

### S: 文 (原則 `fix` モードで適用。個別の例外は規範文に従う)

| ID | 規範                                                                                                                                      | 適用 | 出典と lint との関係                                                                                             |
| -- | ----------------------------------------------------------------------------------------------------------------------------------------- | ---- | ---------------------------------------------------------------------------------------------------------------- |
| S1 | 一文一義。1 文に 2 つの主張や 2 つの手順を入れない。分割点は主張の切れ目で、長さでは判定しない                                            | 全節 | 文化庁、木下。lint の `sentence-length` は超長文だけを止める上限                                                 |
| S2 | 「かもしれない」「と思われる」等の緩和は、根拠なく弱めている場合だけ削る。推量・反実仮想・読者の疑念の提示は不確実性を保つ                | 全節 | gist。lint は `ja-no-weak-phrase` を無効化している                                                               |
| S3 | 助詞の重複は、係り先が読めなくなる場合だけ指摘する                                                                                        | 全節 | lint は `no-doubled-joshi` を無効化している                                                                      |
| S4 | 長い修飾語を先に、節を句より先に置く。読点は語順が逆のときに打ち、分かち書きのテンは打たない。括弧が読点の位置に割り込む形は L3 で扱う    | 全節 | 本多                                                                                                             |
| S5 | 行為者を主語にする。「〜される」「〜となっている」で行為者を隠さない。行為者が本質的に不定な場合と、文脈から自明な場合は指摘しない        | 全節 | gist 視点節、木下。能動と受動の一般的な助言は lint の `ai-tech-writing-guideline` が出すため、行為者の特定に絞る |
| S6 | 空虚な形容 (「非常に」「極めて」)、空虚な動詞 (「深掘りする」「言語化する」)、接続の型 (「正面から」「一方で〜他方で」の対句)、称賛を削る | 全節 | gist LLM 節、テクノエッジ 2026-06-22。lint の `no-ai-hype-expressions` が拾わない語が対象                        |
| S7 | 術語は初出で定義し、以後同じ語で通す。曖昧語 (「もの」「こと」「対応」「適切」) に後退しない                                              | 全節 | gist、SmartHR。表記ゆれは lint の proofdict が拾うため、術語の一貫性の文脈判定に絞る                             |

## 判断の指針

- 指摘と修正は必ず規範 ID に結び付ける。ID に対応しない指摘は出さない。
- 確信が持てる場合だけ指摘する。規範の文言に当てはまるかどうかで迷う箇所は指摘しない。
- 修正は著者の意図を変えない範囲で行う。意図が読めない場合は適用せず、「指摘 (未適用)」の修正案欄に「要判断: 選択肢 1/選択肢 2」の形で書く。
- 同じ規範の同じ問題 (規範違反の型が同じもの) が繰り返すときは、最初の 3 件を箇所付きで挙げ、残りは件数だけ「同 ID の残り N 件」として書く。`fix` モードではすべてに適用する。
- 用語の不統一が項目の節で見つかった場合は L7 に寄せ、S7 は初出定義の欠落と曖昧語への後退に限る。
- 機械層 (lint) が既に出した指摘は pass 1・pass 2 で再掲しない。
- 規範同士が衝突する場合 (D4 の転記禁止と D1 の冒頭説明等) は、文書レベルの規範 (D) を優先し、その旨を「問題」欄に書く。
- 1 つの修正が別の指摘を解消する場合 (節の削除で節順序の問題が消える等) も、指摘は別々の行に立て、修正案欄に依存を書く。ここで省略しないのは依存関係のある別種の指摘で、同 ID の同型反復は前項の集約に従う。

## 報告書式

報告はファイルに書く。呼び出し側が出力先を指定していればそこが正本で、指定はディレクトリとして解釈し、ファイル名は次の規則で付ける。指定が無ければ非汚染領域 (`$CLAUDE_JOB_DIR/tmp` があればそこ、無ければ `mktemp -d` の結果) に `proofread-<対象の basename (拡張子なし)>-<YYYYMMDD-HHMMSS>.md` として書く。貼り付け本文は例外で、「受け取り」節の名前 (`proofread-input-<YYYYMMDD-HHMMSS>.md`) を使う。出力ディレクトリの確保 (`mktemp -d`) は 1 回の実行につき 1 回だけ行う。同じ実行で basename が重複する対象があれば、重複するものの報告名は `proofread-<親ディレクトリ名>-<basename (拡張子なし)>-<YYYYMMDD-HHMMSS>.md` とする。会話にはファイルのパスと集計 1 行だけを返す。集計の形はテンプレートの「集計」行と同じ。整形と提示手段 (エディタで開く等) は呼び出し側が決める。

```markdown
# 推敲報告: <対象の basename>

- 対象: <絶対パス>
- モード: fix | lint
- 実行日時: <YYYY-MM-DD HH:MM>
- 機械層: <実行した完全なコマンド>。preset: <deno.json の alias 先の URL>
- 集計: 機械層 (自動修正 M 件、整形あり | 整形なし、残り K 件)、適用 A 件、指摘 U 件

## 機械層

### 1 回目 (--fix)

<fix モードのみ。出力 O1 をそのまま。末尾に「自動修正 M 件」>

### 2 回目

<出力 O2 (lint モードは O) をそのまま。末尾に分類の 1 行: 「指摘 K 件」「指摘 0 件 (終了コード 0)」「実行不可 (理由)」のいずれか>

### 整形

<fix モードは deno fmt の出力と「整形あり | 整形なし」。lint モードは fmt:check の出力と「整形差分あり | 整形差分なし」>

## 適用した修正 (fix モードのみ)

| 箇所 | ID | 変更前             | 変更後       |
| ---- | -- | ------------------ | ------------ |
| L40  | S2 | 「〜かもしれない」 | 「〜である」 |

## 指摘 (未適用)

| 箇所                        | 節種別     | ID | 問題                                             | 修正案                                           |
| --------------------------- | ---------- | -- | ------------------------------------------------ | ------------------------------------------------ |
| L12「socket の解決手順は…」 | 項目       | L3 | 括弧の補足が 2 つあり係り先が分かれる            | 「…」→「…」                                      |
| L21-23 と L3                | 散文       | D4 | 「発動する場面」節が冒頭段落の言い換え           | 節を削除し冒頭へ統合。採ると D5 の指摘も解消する |
| 節順序 (L13 と L21)         | 散文・項目 | D5 | 例外 (対象外) が前提 (発動する場面) より前にある | D4 の修正で解消する                              |

## 指摘なしの層

- H (誠実さ): 0 件
```

- 箇所は行番号と冒頭の引用で示す。同じ行から複数件出る場合は、該当する文の冒頭を引用して区別する。複数行にまたがる指摘 (節の順序、術語の揺れ等) は行範囲、該当行の併記、または「節順序」のような位置の名前で示す。
- 「節種別」列は当該箇所が属する節の種別を書く。節をまたぐ指摘は併記する。
- 修正案が 1 行に収まらない構成の変更は、表には要点だけ書き、表の直後に補足を書いてよい。
- 0 件の層はその事実を層 (D・P・L・R・S・H) 単位で書く。省略しない。R2 の閾値を超えた行があれば、指摘には上げずに件数と行番号をこの節に注記する。
- `lint` モードでは「適用した修正」節を置かず、集計から「適用」を落とし、すべてを「指摘」に書く。
- 機械層が実行不可のときは、「2 回目」と「整形」の各ブロックに「実行不可 (理由)」の 1 行だけを置く。
- 貼り付け本文が対象で `fix` モードのときは、報告ファイルの末尾に `## 修正後の全文` を置く。
- 集計の機械層は、実行不可なら「機械層 (実行不可)」と書く。
- `lint` モードでは「1 回目 (--fix)」の小見出しを置かず、「2 回目」の小見出しも「実行」に読み替える。

## 持ち込まないもの

- 表記と文法の機械規則 (「分担」節の通り)。
- 文体の指定。
- 一文一行の整形。書籍原稿の版管理向けの規範であり、markdown 文書には当てない。
- 見出し内の太字、箇条書き先頭の絵文字。lint の `no-ai-emphasis-patterns` と `no-ai-list-formatting` の担当。
- 特定の原稿に固有の術語や書式。

## 呼び出し側の責務

- 対象の指定 (ファイルパスまたは本文) と、範囲の指定。
- モードの選択 (省略時は `fix`)。
- 報告ファイルの出力先の指定 (任意) と、提示手段 (コンソール、エディタ等) の選択。
