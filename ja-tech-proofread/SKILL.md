# 日本語技術文章の推敲

日本語の技術文書 (markdown) を読み、機械判定できない層の問題を直す。対象は段落と論証の構成、箇条書き項目の書き方、文の一義性、語彙、事実と意見の区別で、局所的な修正はファイルへ適用し、構成の変更は箇所・規範 ID・理由・修正案の一覧として返す。文書を書き上げた著者、または著者に代わって文書を確認するエージェントが、公開・コミット前の確認に使う。

## 分担

- 表記と文法の機械判定 (全角半角のスペース、カタカナ長音、括弧の幅、句読点、文体の統一、漢字の連続、誇張語、リスト装飾、表記ゆれ) は textlint が担う。この skill は表記規則を持たず、lint の結果を再判定しない。
- lint 設定が意図的に無効化した rule (`ja-no-weak-phrase`、`no-doubled-joshi`、JTF の括弧系) が扱う現象は、機械判定では誤検出が出るために外されている。この skill はそれらを意味の側から判定する (規範 S2・S3)。
- 文体 (常体か敬体か) は扱わない。文体は lint 設定が決める。

## 受け取り

Skill ツールの `args` を次の文法で解釈する。

```
<mode> <path...> [--lint "<command>"]
```

- `mode`: `fix` または `lint`。省略時は `fix`。
  - `fix`: 局所修正 (規範 S・H・R・L3〜L5) をファイルへ直接適用し、構成変更 (規範 D・P・L1・L2・L6・L7) は指摘と修正案に留める。
  - `lint`: ファイルを変更せず、すべての指摘を一覧で返す。
- `path...`: 対象ファイル。省略時は会話で指定された対象 (ファイルパスまたは貼り付けられた本文) を使う。見出し名や行範囲の指定があればその範囲だけを見る。貼り付け本文に `fix` を適用する場合は、修正後の全文を返す。
- `--lint`: 機械層のコマンド (例: `--lint "deno task textlint <path>"`)。省略時は機械層を対象外として報告に明記する。lint 設定 (どの rule を有効にするか) にこの skill は関与しない。

description による自動発動で `args` が無い場合は、mode を `fix`、path を会話文脈から取る。

## 手順

0. 機械層。`--lint` があれば実行し、標準出力・標準エラーと終了コードを「機械層」として報告に転記する。指摘が 0 件なら、出力をそのまま貼った上で「指摘 0 件 (終了コード 0)」と添える。解釈・要約・再判定はしない。
1. 節の分割と種別判定。見出し (`#` で始まる行) ごとに節を切る。見出しが無い文書は全体を 1 節とする。各節について、見出し行・表・コードフェンス・frontmatter を除いた非空行のうち、箇条書き行 (`-`、`*`、`1.` 等で始まる行と、そのインデント継続行) が過半なら「項目」、そうでなければ「散文」とする。
2. pass 1 (構成)。D 規範を文書全体に当てる。P 規範は散文の節に当て、項目の節に並置された独立の散文段落にも当てる。L 規範を項目の節に当て、R 規範を全節に当てる。
3. pass 2 (文と語彙)。S 規範と H 規範を全節に当てる。
4. 適用。`fix` モードなら、pass 1・pass 2 で見つけた局所修正 (S・H・R・L3〜L5) をファイルへ適用する。構成変更は適用しない。`lint` モードなら何も適用しない。
5. 報告。「報告書式」に従って組み立てる。

pass 1 を pass 2 より先に回す。理由: 構成の修正 (段落の分割・項目の統合) で文そのものが消えるため、文の修正を先に出すと無駄になる。

## 規範

各規範は ID で参照する。「適用」列は当てる節種別、「出典」列は規範の根拠を示す。出典の詳細は末尾の「出典」節にある。`fix` モードで直接適用する群は S・H・R と L3〜L5、指摘に留める群は D・P と L1・L2・L6・L7。

### D: 文書 (指摘に留める)

| ID | 規範                                                                                                                                                                 | 適用 | 出典                              |
| -- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---- | --------------------------------- |
| D1 | 冒頭の 1 段落で、何を扱い、いつ使うかを言う。読み手は、文書の型や置き場所 (README、PR 本文等) から決まらない場合にだけ書く                                           | 全節 | Google style、Docs for Developers |
| D2 | 結論と判断を先に置き、根拠と経緯を後に置く。根拠や経緯に相当する記述が無い短い文書には当てない                                                                       | 全節 | 木下 (重点先行)                   |
| D3 | 見出しは扱う対象を指す名詞句にする。1 節が 1 規範だけの仕様文では、規範文そのものを見出しにしてよい                                                                  | 全節 | gist 見出し節                     |
| D4 | 同じ主張を 2 か所に書かない。他の文書や節が持つ内容は参照で済ませ、転記しない                                                                                        | 全節 | gist 冗長節                       |
| D5 | 節の順序は 目的 → 前提 → 本体 (手順・規範・論証) → 例外 → 根拠 とする。根拠を本体の前に長く置かない                                                                  | 全節 | 文化庁、Google                    |
| D6 | 読み手が参照しない固有名・数値・詳細を出さない。「参照しない」とは、文書内で再登場せず、手順の実行にも要らないことを指す。例を足すときは、前の例との差分を前置きする | 全節 | gist 負荷節                       |

### P: 段落 (指摘に留める)

| ID | 規範                                                                                                                               | 適用 | 出典        |
| -- | ---------------------------------------------------------------------------------------------------------------------------------- | ---- | ----------- |
| P1 | 1 段落 1 主題。先頭文で主題を示し、後続文はそれを支える                                                                            | 散文 | 木下、gist  |
| P2 | 段落の先頭で前段との関係を接続表現で示す。関係が文脈から読めるなら省いてよい。1 文だけの段落には当てない                           | 散文 | gist        |
| P3 | 論証は一方向に進める。譲歩 (「確かに〜だが」) の後で必ず論を進める。伏線 (「後述する」) は同じ文書内で回収する                     | 散文 | gist        |
| P4 | 因果を書くときは機構を一文添える。単一の原因に還元しない                                                                           | 散文 | gist        |
| P5 | 否定は否定命題を明示する。「〜ではない」で終えず、何が否定されたかを書く                                                           | 散文 | gist        |
| P6 | 「必ず」「常に」「すべて」には条件を付ける。無条件の全称を書かない                                                                 | 散文 | gist        |
| P7 | 段落を辞書型の定義文で始めない。読者との問答 (「〜だろうか。〜である。」) と著者の弁明の反復を書かない                             | 散文 | gist        |
| P8 | 段落末で直前の内容を要約しない。予告 (「以下では〜を説明する」) と総括 (「以上が〜である」) を置かない。1 文だけの段落には当てない | 散文 | gist LLM 節 |

### L: 項目

出典は執筆コーパス (ルール文書・skill 本文) の実態から起こしたもので、公開基準には無い。L1・L2・L6・L7 は指摘に留め、L3〜L5 は `fix` モードで適用する。

| ID | 規範                                                                                                                                                 | 適用 | 根拠                                                |
| -- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ---- | --------------------------------------------------- |
| L1 | 1 項目 1 規範。強度 (MUST・推奨・禁止・任意) を語で明示する。強度の無い項目は事実の記述として読める形にする                                          | 項目 | 走査して読む前提                                    |
| L2 | 条件 → 帰結の順に書く。例外は同じ項目内に置き、別の項目や節に散らさない。条件を持たない項目には当てない                                              | 項目 | Google (条件を指示の前に)、散らすと参照時に見落とす |
| L3 | 括弧による補足は 1 文につき 1 つまで。2 つ以上必要なら文を分けるか、下位の箇条書きへ下ろす                                                           | 項目 | 長文の主因が括弧の畳み込み                          |
| L4 | 理由は規範の直後に「理由:」で分離する。規範と理由を 1 文に畳まない                                                                                   | 項目 | 規範だけ読みたい読者が理由を飛ばせる                |
| L5 | 3 つ以上の並列は箇条書きにする。文中の並列は「・」で結び、`/` は選択肢 (どれか 1 つ) に限る                                                          | 項目 | 文化庁 (三つ以上は箇条書き)                         |
| L6 | 1 つの項目の内部に複数の段落を書かない。項目が 4 文以上なら小見出しに昇格して散文の節にする。項目の節に並置された独立の散文段落は対象外 (P を当てる) | 項目 | 散文が混ざると P と L のどちらを当てるか決まらない  |
| L7 | 項目間で用語を統一する。同じ対象を別の語で呼ばない                                                                                                   | 項目 | gist (術語で通す)                                   |

### R: 行 (`fix` モードで適用)

| ID | 規範                                                                                                                                                    | 適用 | 根拠                                                  |
| -- | ------------------------------------------------------------------------------------------------------------------------------------------------------- | ---- | ----------------------------------------------------- |
| R1 | 1 行 = 1 段落または 1 項目。段落や項目の途中で改行しない                                                                                                | 全節 | GFM は段落内の改行を空白として描画する                |
| R2 | 1 行が 200 文字 (全角半角を問わず 1 文字を 1 と数える) を超えたら分割を検討する。散文なら P1 で、項目なら L3 または L6 で切る。超過そのものは指摘しない | 全節 | 実測で 200 文字超はルール文書の 16%、skill 本文の 13% |

### S: 文 (`fix` モードで適用)

lint が意図的に開けた穴を意味の側から判定する群。lint の rule と重なる指摘は出さない。

| ID | 規範                                                                                                                                      | 適用 | 出典と lint との関係                                                                                             |
| -- | ----------------------------------------------------------------------------------------------------------------------------------------- | ---- | ---------------------------------------------------------------------------------------------------------------- |
| S1 | 一文一義。1 文に 2 つの主張や 2 つの手順を入れない。分割点は主張の切れ目で、長さでは判定しない                                            | 全節 | 文化庁、木下。lint の `sentence-length` は超長文だけを止める上限                                                 |
| S2 | 「かもしれない」「と思われる」等の緩和は、根拠なく弱めている場合だけ削る。推量・反実仮想・読者の疑念の提示は不確実性を保つ                | 全節 | gist。lint は `ja-no-weak-phrase` を無効化している                                                               |
| S3 | 助詞の重複は、係り先が読めなくなる場合だけ指摘する                                                                                        | 全節 | lint は `no-doubled-joshi` を無効化している                                                                      |
| S4 | 長い修飾語を先に、節を句より先に置く。読点は語順が逆のときに打ち、分かち書きのテンは打たない。括弧が読点の位置に割り込む形は L3 で扱う    | 全節 | 本多                                                                                                             |
| S5 | 行為者を主語にする。「〜される」「〜となっている」で行為者を隠さない。行為者が本質的に不定な場合と、文脈から自明な場合は指摘しない        | 全節 | gist 視点節、木下。能動と受動の一般的な助言は lint の `ai-tech-writing-guideline` が出すため、行為者の特定に絞る |
| S6 | 空虚な形容 (「非常に」「極めて」)、空虚な動詞 (「深掘りする」「言語化する」)、接続の型 (「正面から」「一方で〜他方で」の対句)、称賛を削る | 全節 | gist LLM 節、テクノエッジ 2026-06-22。lint の `no-ai-hype-expressions` が拾わない語が対象                        |
| S7 | 術語は初出で定義し、以後同じ語で通す。曖昧語 (「もの」「こと」「対応」「適切」) に後退しない                                              | 全節 | gist、SmartHR。表記ゆれは lint の proofdict が拾うため、術語の一貫性の文脈判定に絞る                             |

### H: 誠実さ (`fix` モードで適用)

| ID | 規範                                                                                                                                                             | 適用 | 出典        |
| -- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---- | ----------- |
| H1 | 事実と意見を分ける。推量には推量の語を残し、断定には根拠を添える。確認の語 (「確認した」等) を伴わない断定の根拠不足はここで扱う                                 | 全節 | 木下        |
| H2 | 未確認のことを確認したように書かない。「動作を確認した」「実測した」等、確認を明言する語は実際に行った場合に限る。確認の有無が読めない場合は適用せず指摘に留める | 全節 | gist        |
| H3 | 根拠は一次資料に求め、出典を示す。二次情報は二次と書く                                                                                                           | 全節 | gist        |
| H4 | 演出 (溜め、決め台詞、本文中の太字の強調、命令調、劇的転回、ひねった比喩) は要所に限る。技術文書では原則使わない。見出し内の太字は lint の担当で対象外           | 全節 | gist 演出節 |

## 判断の指針

- 指摘と修正は必ず規範 ID に結び付ける。ID に対応しない指摘は出さない。
- 確信が持てる場合だけ指摘する。規範の文言に当てはまるかどうかで迷う箇所は指摘しない。
- 修正は著者の意図を変えない範囲で行う。意図が読めない場合は適用せず「要判断」とし、選択肢を 2 つまで添える。
- 同じ規範の同じ問題 (規範違反の型が同じもの) が繰り返すときは、最初の 3 件を箇所付きで挙げ、残りは件数だけ「同 ID の残り N 件」として書く。`fix` モードではすべてに適用する。
- 用語の不統一が項目の節で見つかった場合は L7 に寄せ、S7 は初出定義の欠落と曖昧語への後退に限る。
- 機械層 (lint) が既に出した指摘は pass 1・pass 2 で再掲しない。
- 規範同士が衝突する場合 (D4 の転記禁止と D1 の冒頭説明等) は、文書レベルの規範 (D) を優先し、その旨を「問題」欄に書く。
- 1 つの修正が別の指摘を解消する場合 (節の削除で節順序の問題が消える等) は、修正案欄にその依存を書く。

## 報告書式

```markdown
## 機械層

<lint の出力をそのまま。0 件なら出力の後に「指摘 0 件 (終了コード 0)」。コマンド未供給なら「lint コマンド未供給のため対象外」>

## 適用した修正 (fix モードのみ)

| 箇所 | ID | 変更前             | 変更後       |
| ---- | -- | ------------------ | ------------ |
| L40  | S2 | 「〜かもしれない」 | 「〜である」 |

## 指摘 (未適用)

| 箇所                        | 節種別 | ID | 問題                                   | 修正案                                           |
| --------------------------- | ------ | -- | -------------------------------------- | ------------------------------------------------ |
| L12「socket の解決手順は…」 | 項目   | L3 | 括弧の補足が 2 つあり係り先が分かれる  | 「…」→「…」                                      |
| L21-23 と L3                | 散文   | D4 | 「発動する場面」節が冒頭段落の言い換え | 節を削除し冒頭へ統合。採ると D5 の指摘も解消する |

## 指摘なしの層

- H (誠実さ): 0 件
```

- 箇所は行番号と冒頭の引用で示す。同じ行から複数件出る場合は、該当する文の冒頭を引用して区別する。複数行にまたがる指摘 (節の順序、術語の揺れ等) は行範囲、該当行の併記、または「節順序」のような位置の名前で示す。行番号が取れない (貼り付け本文等) 場合は引用だけでよい。
- 「節種別」列は当該箇所が属する節の種別を書く。節をまたぐ指摘は併記する。
- 修正案が 1 行に収まらない構成の変更は、表には要点だけ書き、表の直後に補足を書いてよい。
- 0 件の層はその事実を層 (D・P・L・R・S・H) 単位で書く。省略しない。R2 の閾値を超えた行があれば、指摘には上げずに件数と行番号をこの節に注記する。
- `lint` モードでは「適用した修正」節を置かず、すべてを「指摘」に書く。

## 持ち込まないもの

- 表記と文法の機械規則 (「分担」節の通り)。
- 文体の指定。
- 一文一行の整形。書籍原稿の版管理向けの規範であり、markdown 文書には当てない。
- 見出し内の太字、箇条書き先頭の絵文字。lint の `no-ai-emphasis-patterns` と `no-ai-list-formatting` の担当。
- 特定の原稿に固有の術語や書式。

## 呼び出し側の責務

- 対象の指定 (ファイルパスまたは本文) と、範囲の指定。
- lint コマンドの供給。lint 設定 (どの rule を有効にするか) もこの skill は関与しない。
- 報告の提示手段の選択 (コンソール、エディタ、ファイル等)。
- モードの選択 (省略時は `fix`)。
