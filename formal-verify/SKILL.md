# formal-verify: 形式手法による AS-IS 検証

実装コードを de-facto 仕様とみなし、機械検査で「実装が主張している仕様」と「暗黙に決めている挙動」を炙り出す手順。やることは 3 段。

1. **吸い出し（extract）**: コードから「宣言された仕様」と「暗黙の挙動」を分けて抜く
2. **形式化して反例探索（refute）**: 主張をモデル化し、全入力・全順序で本当に成り立つかを機械に攻撃させる
3. **突き合わせ（reconcile）**: 出た反例を「これは意図か」とドメインに問う。意図なら仕様として明文化、意図でないならバグ

最終成果物は証明の山ではなく、台帳（実装の主張・機械検査の結果・ドメインへの確認質問、の 3 列）。反例はバグ報告であると同時に認識合わせの会話の起点になる。

## 適用判断

### 適用する場面（いずれかに該当したら候補）

- 有限・決定的な判定ロジックがある（入力の同値類が有限に列挙できる validation・分岐）
- 冪等性・順序・再実行・crash 復帰・日次ガード・二重適用が論点
- spec docs が無い/あてにならないレガシーバッチ等の AS-IS 起こし（暗黙挙動が多い）
- クロス境界のデータ契約（外部連携ファイルのフォーマット・enum・単位の合意）
- バグ調査で暗黙挙動を炙り出したい（無音経路・想定外分岐の特定）

### 適用しない場面（anti-trigger）

- 確率的・統計的性質（期待値・分布）
- UI・画面挙動の検証（画面操作・シナリオ試験は本 skill の対象外）
- 分岐の無い薄い CRUD（判定ロジックが無く、列挙する対象が無い）
- 性能・ボトルネック（判定ロジックでなく処理速度が論点なら本 skill の対象外）
- 既に単体テストで全ケース網羅済みの領域

### やめ時（限界効用）

全部を形式化しない。主要な不変条件・危険な穴・クロス境界契約を押さえたら、次は新規の形式化より、溜まった反例・確認質問をドメインと捌く方がレバレッジが高い。大物を出し切った後の確認的なだけの命題の量産はやめる。

## ワークフロー全体像

各ステップの詳細は、手を動かす段階で該当の references ファイルを Read する。

1. **吸い出し**（`references/extraction.md`）: 対象コードを読み、宣言された仕様と暗黙の挙動を分けて抽出する。8 つの問いを機械的に投げ、バグ型カタログで「ありそう」を当てる
2. **純関数モデル化**（`references/enumeration-harness.md`）: 判定ロジックを観測可能な入力 → 結果の純粋関数 `predict` に写像する。配管（I/O・フレームワーク・DB）は持ち込まない
3. **層 1: 全列挙 + named invariant**（`references/enumeration-harness.md`）: 同値類の直積を deno で全列挙し、名前付き不変条件を検査する
4. **broken-variant**（`references/enumeration-harness.md`）: ガードを故意に外したモデルで検査が赤になることを確認する（検査の実効性証明）
5. **層 2 要否判定**（下記）: 実行列に対する性質が論点なら TLA+ に進む。層 1 で足りるならここで台帳へ
6. **層 2: TLA+ / TLC**（`references/tla.md`）: 実行ライフサイクル（再実行・crash・日跨ぎ等）の不変条件をモデル検査する
7. **台帳**（`references/ledger-format.md`）: 主張毎に「実装の主張・機械検査の結果・確認質問」の 3 項目を記し、冒頭にカバレッジ宣言（同値類の由来・無音経路の一覧・持ち越し状態の対応表）を置いて、指示された出力先（ファイル/issue tracker 等）へ出力する。宣言に「未実施」が残る場合は理由を書くか、ハーネスに戻って埋める

## 層 2（TLA+）の要否判定

- 要否は対象単位でなく性質単位で判定する。主張を「1 回の適用で決まる性質」と「実行列に依存する性質」に仕分け、前者を層 1・後者を層 2 で検査する（両層併用が通常形。層 2 に進んでも層 1 は省略しない）
- トリガは選言で、優先順位を付ける: 実行を跨ぐ/持ち越し状態に依存する性質は軸数に関わらず層 2。後述の 2 軸ルールは、それ以外で層 1 に見える性質を層 2 に格上げする補助基準にすぎない
- 一次基準: 性質が 1 回の実行を跨ぐか、実行間で持ち越す状態（履歴・残置ファイル等）に依存するか。跨ぐ・依存するなら層 2 に進む
- 実行境界の定義:「1 回の実行」とは持ち越し状態が永続層から再構成される処理単位を指す。バッチなら 1 回の起動、リクエスト駆動のサービスなら 1 リクエスト処理を 1 実行と数える
- crash 等の実行時非決定が生む状態でも、性質の評価時点で層を決める: 単一実行の終端までに閉じる性質（中断時の終端状態の分類等）は層 1、次の実行の挙動を含む性質（再実行での再処理等）は層 2
- 検査したい性質が 1 回の関数適用で表現できる（行単位の判定・validation・出力分類）なら層 1 で足りる。この場合、tlc の前提確認にも進まない（「ツール前提」の縮退とは別。要否判定で不要なら確認自体が不要）
- 探索空間の軸は実行時の非決定（crash・日跨ぎ）に限らず、実行毎に固定される設定（CLI フラグ・モード）も 1 軸として数える。層 1 のファイル単位シミュレータで擬似再現できるのは 1 軸までで、2 軸以上の組合せになったら TLA+ に切り替える
- 軸として数えるのは実行境界（1 回の `predict` 実行）を跨いで持ち越す状態だけ。1 実行内で消費される揺らぎ（同一ファイル内の重複キー・dryrun と実行の件数比較）は軸数に関わらず常に層 1 の守備範囲で、層 2 の 2 軸判定に加算しない

## MUST 群

- MUST: モデルは実コードから写像する。doc・記憶・要約からモデルを組まない。変換を 1 つ取り違えると偽の証明になる（例外: 対象が判定を外部パッケージへ委譲している場合はピン版の実物をオラクルとして import するのが忠実な写像。`references/enumeration-harness.md` を見よ。依存の再実装はそれ自体が偽モデル）
- MUST: broken-variant 無しの緑を成果としない。わざと壊したモデルで検査が赤になることを確認するまで「常に緑 = 何も検証していない」を疑う
- MUST: 台帳は 3 列（実装の主張・機械検査の結果・ドメインへの確認質問）で書く。投稿先が使えない文脈での縮退は `references/ledger-format.md` の規定に従う
- MUST: モデル化元（ファイル・メソッド・行）と捨象した要素を台帳冒頭に明記する。「モデルで成立 = 実装で成立」とは書かない（model↔code gap は常に残る）
- MUST: 無音経路（エラーにも失敗一覧にも載らないスキップ経路）は「何が黙って失われるか」まで突いて台帳の主張に昇格させる（プローブと層のルーティングは `references/enumeration-harness.md` の規定に従う）。応答が一様な処理（常に同じ結果を返すハンドラ等）では、応答・ログから区別できない状態・副作用の分岐も無音経路として扱う。成功経路そのものは無音経路に数えない（一様応答による経路の区別不能性は別主張として立てる）

## model ↔ code gap を実データで詰める（trace-checking）

モデルは「書いたモデル」を検証するのであって実コードそのものではない。gap の広さは対象で変わる。対象がデータ（設定・ルール）なら実データを直接列挙に食わせられるので gap は狭い。対象が命令型・並行コード（主に層 2）なら手で抽象するぶん gap は広く残る。

gap を最も強く詰める一手が trace-checking。実システムの操作ログ（実際に起きたイベント列）を採取し、「その観測列がモデルの正当な振る舞いか」を replay で検査する。これで「実装が naive/atomic どちらの仕様を refine しているか」を実データで確定できる。抽象モデルと実挙動を繋ぐ手段で、層 2 の広い gap が結論を左右しうる場面で使う。

- 使い所: 層 2 で命令型・並行の挙動をモデル化し、抽象が実装より強い/弱い仮定を置いていないかを実データで裏取りしたいとき。層 1（データ対象で gap が狭い）では通常不要
- 手順:
  1. 実行時に観測可能なイベント列（適用・スキップ・crash・再実行等）をログとして採取する
  2. モデルの遷移で同じイベント列を再生し、各ステップがモデルの `Next` で許される遷移かを照合する
  3. 逸脱したら「モデルが実装を取りこぼしている」か「実装がモデルに無い遷移をしている」かを切り分け、台帳の model ↔ code ギャップ節に記す
- 限界: trace-checking は採取したログに現れた経路しか裏取りできない（未観測の稀な interleaving は保証しない）。broken-variant による検査実効性証明の代わりにはならない。両者は別レイヤーの担保

## ツール前提

- **deno**: 層 1 の全列挙ハーネスの実行に使う。`command -v deno` で確認し、無ければ実行環境に導入する。理由: 導入方法は環境に依存するため指定しない
- **tlc**: 層 2 の TLA+ モデル検査に使う。要否と tlc の扱いは次の決定表に従う。

  | 層 2 要否判定         | tlc の状態                                         | 行動                                                                                                                                                                                      |
  | --------------------- | -------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
  | 不要（層 1 で足りる） | 問わない                                           | tlc の確認にも進まない。層 1 のみで成立                                                                                                                                                   |
  | 必要                  | 使える（`references/tla.md` の前提確認が通る）     | そのまま層 2 を実行する                                                                                                                                                                   |
  | 必要                  | 使えない（未導入・破損・ポリシーによる実行禁止等） | 使えない原因を解消できるなら解消して実行する（未導入なら導入等）。解消できなければ層 2 をスキップし、台帳に「層 2 未実施（tlc 使用不可）」と明記して層 1 のみで成立（縮退して止まらない） |
- Z3/SMT は扱わない。decidable な述語検証も本 skill では有限の同値類列挙で代替する。導入が必要になったら別途検討する

## 成果物と運用

- 台帳の正本は指示された出力先（ファイル/issue tracker 等）とする
  - docs/配下や作業ツリー直下に台帳を既定で置かない
  - 出力先が指示されない場合は、ハーネスと同じ非汚染領域（job 一時領域等、リポジトリ/worktree の作業ツリー外）へファイルとして出力し、そのパスをユーザに提示する
  - 台帳から確定した挙動（HOLDS = 契約、確認質問が解決した VIOLATED）のみを spec docs（AS-IS）へ反映し、spec 本文での根拠はモデルではなく実装へのコード参照で示す（spec docs のコード参照規約がある場合はそれに従う）
- ハーネスは既定で使い捨て。job 一時領域等で実行し、リポジトリにコミットしない。モデルベースのハーネスは既定では資産化しない。理由: model↔code gap が黙って腐るため
- CI 資産化（契約ロック）への昇格は次の 3 条件をすべて満たし、かつユーザ承認を得た場合に限り別タスクで行う。置き場所・CI 組込みの設計はその別タスクの範囲とする
  - (a) HOLDS の性質が仕様として確定しており壊れると事故になる
  - (b) 対象コードに今後変更が見込まれる
  - (c) broken-variant self-check 済み
