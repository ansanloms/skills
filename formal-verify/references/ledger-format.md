# 台帳の書式

検証の最終成果物。主張毎に「実装の主張/機械検査の結果/ドメインへの確認質問」の 3 列で書き、指示された出力先（ファイル/issue tracker 等）へ出力する（正本。SKILL.md「成果物と運用」）。出力先が未指定・未確定の実行文脈では、リポジトリ/worktree の作業ツリーを汚さない場所（ハーネスと同じ job 一時領域等）へファイルとして台帳を出し、そのパスをユーザに提示する。作業ツリー直下や docs/配下には既定で置かない。台帳冒頭に投稿先が未確定である旨を明記する（縮退して止まらない）。縮退時も評価節はそのまま台帳ファイル内に書き、「起票判断はユーザに委ねる」の運用を維持する。

## 台帳の全体構成

```markdown
# <対象> 形式手法検証 台帳

対象: <モデル化元のファイルパス（メソッド・行範囲まで）>
手法: Layer 1 = <ハーネス名・列挙規模>、Layer 2 = <TLA+ モジュール名・構成数>（未実施ならその旨と理由）
モデルは実コードから直接写像した（doc からではない）。

## C1. <主張の見出し（一文で挙動を言い切る）>

- **実装の主張**: ...
- **機械検査の結果**: ...
- **確認質問**: ...

（C2, C3, ... と続ける）

## model ↔ code のギャップ

（モデルが単純化した点の列挙）

## broken-variant（検査が効いていることの証明）

（反転した invariant の一覧）

## 評価: spec docs への反映とバグ候補

（反映区分の仕分け）
```

## 各列の書き方

### 実装の主張

- 「実装は〜と主張している」を一文で。**宣言された仕様**（コメント・エラーメッセージ由来）か**暗黙の挙動**（実装が確定させているだけ）かを区別し、暗黙なら「（暗黙）」と付ける
- 根拠となる実装の参照（ファイル・メソッド・行番号）を必ず添える

### 機械検査の結果

- verdict を**HOLDS**/**VIOLATED**で書き、どの invariant・どの構成（cfg）で確認したかを添える
- VIOLATED には **witness（反例）**を必ず残す。層 1 なら反例セルの入力と Outcome、層 2 なら最小の再現シナリオ（アクション列と最終状態）
- 反例志向で立てた invariant（素朴な期待を否定させる目的のもの）の VIOLATED は、その旨を書く（「これは『中断時は DB 無傷』という素朴な期待への反例であり、prefix コミットの witness」等）。VIOLATED = バグとは限らない
- 検査の外にある主張（コードレビュー由来等）を台帳に載せる場合は「未検査」と明記し、機械検査の結果と混ぜない

### ドメインへの確認質問

- **「これは意図か」をドメインに問う形**で書く。意図なら仕様として明文化、意図でないならバグ、の二択に落ちる質問にする
- 発生条件と実害を添える（「〜が発生しうるなら、(1) ... (2) ... の 2 点が実害」）。質問の優先度が判断できる
- 実害は直接効果で止めず、**下流への波及まで追う**。書込みを伴う反例なら、その書込みが持ち越しガードを消費する副作用（後続の正当な行が同日黙殺される等）・カウンタ・レポート/メールへの影響を確認して実害に含める
- 質問が無い（確定挙動）なら「なし」とし、契約（regression guard）としてロック可能である旨を書く

## 台帳冒頭の必須事項（MUST）

- モデル化元: ファイル・メソッド・行番号の列挙。対象がスニペット・貼付コードとして供給されディスク上に無い場合は、写しを非汚染領域に保存してそれをモデル化元とし、稼働コードとの一致が外部前提であることを「model ↔ code のギャップ」節に明記する
- 捨象した要素: モデルが単純化した点（例: 在庫値を捨て適用回数を property carrier にした・並行実行は非対象・メール送信の失敗は非モデル）。台帳の結論を左右しうるものは「model ↔ code のギャップ」節で個別に明示する
- モデル化時に参照できなかった依存コード（スニペット外の初期化・外部関数等）: 主張として立てず「model ↔ code のギャップ」節に列挙し、挙動が結論を左右しうるなら評価節の確認事項に落とす
- 「モデルで成立 = 実装で成立」とは書かない
- **カバレッジ宣言**: 次の 3 点を表または箇条書きで宣言する。実施しなかった系統は「未実施」とその理由を書く（黙って省略しない。宣言できない項目が残っていたら、台帳を書く前にハーネスへ戻る）
  1. 同値類の由来: コード分岐由来/ドメイン入力契約由来/コード空間の系統走査由来のそれぞれについて、採った入力クラスを列挙する（由来は排他でなくてよい。1 クラスが複数の由来に該当するなら最も強い根拠の下に置く）
  2. 無音経路の一覧: 検出した無音経路（エラーにも失敗一覧にも載らずに accept/skip する return/exit 地点）と、それぞれに対応する台帳の主張番号。粒度は**個別の return / exit 地点毎**に 1 行（まとめてよいのは同一の主張番号に対応する場合のみ）。理由付きで拒否する経路（reason を伴う `return false` 等）は無音経路ではないので、この一覧の対象外
  3. 持ち越し状態のインベントリ（層 2 実施時）: 状態 × 無効化する境界イベント × 発火させた cfg × 通算 invariant × 対応する主張番号の対応表。層 2 未実施の場合、この対応表は「未実施 + 理由」と宣言する。吸い出しで判明した持ち越し状態の一覧を情報として別掲してよいが、対応表そのものとは区別する

## broken-variant 節

- どのガードを外し、どの invariant が HOLDS → VIOLATED に反転したかを列挙する
- self-check（期待 verdict 表との突き合わせ）の結果を書く
- 反転が 1 つも無い場合、その検査はガードを見ていない。ハーネス側を直してから台帳を書く

## 評価節（spec docs への反映とバグ候補の仕分け）

台帳の各主張を次の区分に仕分ける。

- **仕様として記述（HOLDS = 契約）**: そのまま AS-IS spec に書ける確定挙動
- **確認事項として記述**: 意図の確認が要る挙動。spec には確認中として扱う（spec docs 側に未確認の値の扱いの規約があればそれに従う）
- **バグ候補としてドメインに提起**: 実害のある反例。起票（issue 化）の判断はユーザに委ねる
- **未検証として保留**: 層 2 未実施等で verdict が無い主張。参考 witness を添えてよいが上の 3 区分に混ぜず、次アクション（`references/tla.md` の縮退手順参照）と共に保留として明示する

spec docs へ反映する際の根拠はモデルではなく実装へのコード参照で示す。台帳（モデル・invariant 名）を spec 本文に持ち込まない。
