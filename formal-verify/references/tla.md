# 層 2: TLA+ / TLC によるライフサイクルモデル検査

実行列に対する不変条件 — 実行間で持ち越す状態・crash/再実行/日跨ぎ・非決定な順序 — を、起こりうる全シナリオの総当たりで検査する。層 1（1 回の関数適用の全列挙）で表現できない性質だけをここへ持ち込む（要否判定は SKILL.md）。

## 前提確認（縮退手順）

層 2 に入る前に TLC が**実際に走る**かを確認する。`command -v tlc` の PATH ヒットだけでは不十分で、PATH 上のラッパが JRE 欠落等で動かないことがある。逆にラッパが JRE を同梱していて動く場合もある。空・自明なモデルへの試走（smoke-run）まで通って初めて「有り」とみなす。

- 有る（PATH に在り、かつ smoke-run が通る）: そのまま進む
- 無い: 実行環境に tlc（TLA+ ツールボックスの TLC モデルチェッカ）を導入する。導入方法は環境に依存するので指定しない
- それでも使えない: 層 2 をスキップし、台帳に「層 2 未実施（tlc 無し）」と明記して層 1 のみで成立させる。エラーで作業を止めない
- MUST: スキップした層 2 が**主要論点**（分析を動機づけた性質そのもの。例: 再実行・crash 復帰での二重適用）に当たる場合、「層 1 で成立」で未検査を隠さない。台帳に「主要論点は未検査（層 2 未実施）」と明示し、次アクションを必須項目として立てる: (a) tlc を導入して層 2 を実行する、(b) `references/enumeration-harness.md` のファイル単位シミュレータで実行列を層 1 に擬似再現して部分的に押さえる（1 軸まで）、(c) trace-checking で実ログと突き合わせる（SKILL.md 参照）。主要論点が機械検査ゼロのまま台帳を確定挙動として閉じない

## モデルの書き方

### 状態変数の選定と抽象化

- **値を捨て、property carrier を残す**。在庫の数値そのものは要らず「キー毎の適用回数」だけで二重適用は検査できる。検査したい性質を運ぶ最小の変数を選ぶ
- 実行間で持ち越すもの（ガードの実体となる履歴・残置ファイルの有無）は必ず変数にする。ここが層 2 の存在理由
- 入力（ファイル内容等）は種別の有限集合に抽象化する（例: ok/bad/corrupt の 3 値）。値レベルの意味論は層 1 の担当で、二重に持たない
- 非決定性は `Next` の選言（`\/`）で表す: crash するかもしれない・日を跨ぐかもしれない・どのファイル変種か、を機械に全部試させる

### モジュールの構成

- ヘッダコメントにモデル化元（ファイル・メソッド・行番号）と捨象した要素を列挙する（台帳冒頭と同内容。MUST）。ヘッダは `\*` の行コメントで書く。ブロックコメント `(* ... *)` は**入れ子で解釈される**ため、パス名や散文に `(` が混ざるとパースエラーになる
- アクションは実装の意味論単位で分ける（1 行処理・validation 失敗・破損中断・crash・正常完了・再実行・日跨ぎ再実行、等）。各アクションに実装の参照をコメントで残す
- 状態爆発を防ぐため、キー集合は 2 要素程度・再実行回数は定数（`MaxRuns == 2` 等）で上界を切る。二重適用の検出には 2 回で足りる

### invariant

証明したい性質に名前を付けて宣言する。反例志向で立ててよい（「中断時は DB 無傷」のような素朴な期待を invariant にして、TLC に破らせる → prefix コミットの witness が得られる）。

- MUST: **invariant をガードのスコープに合わせて弱めない**（ガードが「当日」なら invariant も「日毎」にする、はトートロジー化で、境界破れが黙る）。持ち越しガードには**通算**の invariant（例: 同一入力の適用回数は全期間で ≤ 1）を必ず 1 本立てる。境界イベント（日跨ぎ等）でそれが破れたら、「破れは正当か」をドメインへの確認質問として台帳に載せる — invariant 設計で正当化して片付けない

## cfg を構成毎に分ける

検査したいシナリオ（モード × 非決定性の有効/無効）毎に `.cfg` を分け、CONSTANTS で切り替える。1 つの cfg に全部盛ると反例がどのシナリオ由来か読めなくなる。

- MUST: cfg の構成行列は**持ち越し状態のインベントリから導出する**。実行間で持ち越す状態を列挙し、各状態を無効化・温存する境界イベント（例: 日付キーのガード → 日跨ぎ、残置ファイル → 再実行、迂回モード → ガード無効）を Next のアクションに入れ、それぞれ**最低 1 つの cfg で発火**させて台帳の主張に対応させる。モデルに入れたのに cfg で発火させない境界イベントを残さない（探索されない軸は台帳から抜ける）

```
\* Example_normal.cfg — 通常モード・日跨ぎ無し
SPECIFICATION Spec
CONSTANTS
  Mode = "normal"
  DayRollover = FALSE
INVARIANTS
  NoDoubleApply
  BackupOnlyIfCleanRun
```

次のコマンドで実行する。ライフサイクルモデルは終端状態（正常完了・中断）を自然に持つため、`-deadlock`（deadlock 検査の無効化）を付ける。

```bash
tlc -deadlock -config Example_normal.cfg Example.tla
```

成立時は `Model checking completed. No error has been found.`、違反時は `Invariant <名前> is violated.` と反例トレースが出る。

層 1 の期待表 self-check と同様に、**構成 × invariant の期待結果（違反あり / なし）を表で持ち**、TLC の出力と突き合わせてから台帳に載せる。目視の印象で verdict を書かない。

## 反例トレースの読み方

- トレースは Init からの状態列（State 1, 2, ...）。各状態でどのアクションが取られ、どの変数が変わったかを追い、**最小の再現シナリオ**として台帳の witness に要約する（例: `StepOk(k1 適用) → Crash → NextDayRerun(hist リセット) → StepOk(k1 再適用) → applied[k1]=2`）
- 反例が「モデルの書き誤り」由来でないかを必ず疑う。実装の該当行と突き合わせ、モデルが実装より強い/弱い仮定を置いていないか確認してから台帳に載せる
- TLC は最短反例を探すため、トレースが想定より短いことがある（例: 再実行を待たず 1 回の実行内で違反が成立）。それ自体が発見になる

## broken-variant

層 2 でも実効性を証明する。ガードに相当する条件（例: `GuardBlocks`）をモデルから外した変種（または cfg の CONSTANTS 切り替え）で、HOLDS だった invariant が違反に反転することを確認する。層 1 で broken-variant 済みの性質を層 2 が引き継ぐ場合は、層 2 側では構成の対比（ガード有り cfg = 緑/ガード迂回 cfg = 赤）で代替してよい。要件は invariant 単位で課す: **どの層で初めて現れた HOLDS invariant も、それを反転させる break / cfg 対比を 1 つ持つ**（層 2 で新規に立てた HOLDS invariant も、引き継ぎでなく単独で反転先を要する）。
