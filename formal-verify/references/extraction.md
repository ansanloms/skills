# 吸い出し（extract）: コードから仕様を抜く

対象コードを読み、**「宣言された仕様」と「暗黙の挙動」を必ず分けて**メモする。この分離が台帳の「実装の主張」列の材料になる。

## 宣言された仕様の在り処（intent が書かれている場所）

- **コメント**、特に「なぜ」を語るもの。「〜のときはスキップする」等は仕様の宣言。「元のコードがそうなっていた」「理由は分からない」系のコメントは化石（fossil）の印 — 仕様か惰性か要確認
- **テスト名・アサーション**: 境界仕様そのもの。期待値の並びも仕様
- **ガード節・例外・error 返し**: 前提条件と fail-mode を宣言している
- **enum 定義・定数テーブル・スキーマ制約**: 取りうる値と、値↔意味の対応

## 暗黙に決めている挙動（どこにも書いてないが実装が確定させている）

- **default 値・空 / null の扱い**: 未設定が「全許可」か「全拒否」か。空コレクションの真偽
- **エラー時の分岐**: 未検出/parse 失敗/タイムアウトで、true/false/例外のどれに倒れるか
- **順序依存と短絡**: 適用順で結果が変わるか（副作用があるか）
- **値が「決定される」場所**: フォールスルーの優先順位、複数ソースからどれを採るか
- **クロス境界の変換**: シリアライズ/単位/タイムゾーン/フォーマット
- **誰が制御できる入力か**: システムが付ける値 vs 外部が自由に付けられる値（信頼境界）
- **言語 semantics の罠**: PHP なら `empty()`（`"0"` は空だが `"-0"` は空でない）・`in_array` 非 strict の緩和比較・文字列と数値の暗黙変換等。宣言された仕様と実際の判定がずれる典型源

## 8 つの問い（各述語・各機構に対して機械的に投げる）

1. 空/未設定のとき何が起きるか。
2. エラー/取得失敗のとき true か false か例外か（fail-open/fail-close）。
3. 否定（NOT/除外/inverse）をかけると、上の答えはどう化けるか。
4. 境界はどちら向きか（`>` か `>=` か、端点を含むか）。
5. 同時に 2 つ来たらどうなるか。片方の結果がもう片方に間に合うか。
6. この値は誰が決めるか。信頼できない相手が差し替えられるか。
7. このループ/リトライは何で止まるか。止めているのは本質的な条件か、たまたまか。
8. 2 つのシステムがこのデータで合意しているか（レイアウト・enum・単位）。

## バグ型カタログ（対象選定のあたり付けに使う）

経験上この型が繰り返し出る。チェックリストとして使い、「ありそう」な型から検証対象を選ぶ。

### 純粋述語・設定系（層 1 = 全列挙向き）

- **矛盾設定（dead config）**: 条件の連言が充足不能 = どんな入力でも通らない
- **冗長・内包（subsumption）**: 片方の条件が他方を含意し、設定されているのに効いていない
- **被覆の穴 / dead branch**: どの選択肢にもマッチしない入力がある/どの入力でも選ばれない枝がある
- **表現の等価性**: 旧形式↔新形式、リファクタ前後が同じ意味かを全入力で確認

### 実行列・時間系（層 2 = TLA+ 向き）

- **read-modify-write レース / TOCTOU**: 読んで判定して書く、が分離していると古い値で両方通る
- **判定と記録の分離**: 判定は今すぐ、記録は後で。判定時点で記録がまだ無い → ガードをすり抜ける
- **原子性 / torn read**: 共有リソース（ファイル・スナップショット）の途中状態を読む
- **収束 / runaway（停止性）**: リトライ・引き上げのループが有界回で止まるか
- **伝搬 / 最終整合**: commit した変更がいつか必ず反映されるか。crash + 再起動で更新が失われないか
- **冪等性**: リトライ・再実行で二重カウント・二重適用しないか。ガードの有効期間（当日限定等）

### 境界・信頼系（どちらでも）

- **fail-open / fail-close の非一貫**: エラー時の振る舞いが機構ごとに食い違う
- **エラーを boolean に畳む × 否定**:「不一致」と「エラー」を同じ false に畳んだ実装に否定をかけると、エラー時にマッチへ化ける。最も見落とされやすい
- **空集合の意味**: 空の AND = 真（常時マッチ）、空の OR = 偽、が階層で不整合
- **クロス境界の表現契約**: 2 つのシステムが共有する enum/レイアウト/単位の齟齬
- **欠けた前提条件**: 負のサイズ・空配列で落ちる。ガードが呼び出し側にしか無い

## 吸い出しの出力

次の 2 つをメモとして残し、モデル化の入力にする。

- 主張リスト:「実装は〜と主張している（宣言/暗黙）」の列挙。各主張に検証したい性質（成立を証明したいのか、反例が欲しいのか）を付ける
- モデル化元の記録: ファイル・メソッド・行番号。台帳冒頭に転記する
